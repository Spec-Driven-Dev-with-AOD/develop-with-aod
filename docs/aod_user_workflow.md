# From an App Idea to a Program with AOD

Invoke `$develop-with-aod` in Codex. The skill supplies the AOD model, formats, schemas, lint rules, and stage instructions automatically; do not attach those framework files. Supply the application intent and name or attach only the application-specific artifacts requested for the selected stage. Review and approve the results; the AOD user remains responsible for the intended behavior and implementation choices.

Complete one stage at a time. Continue with the next stage in the same task by default, explicitly naming the stage. Start a fresh task only when an independent review is desired, the existing conversation has become long or confusing, or a clean implementation context would be beneficial. A fresh task may also be useful for a controlled evaluation, but memory configuration is an optional test condition rather than an AOD workflow prerequisite.

Select a stage by writing `Stage: <stage>` after the skill name. The six stage identifiers are `create-package`, `review-package`, `lint-package`, `logical-preview`, `implementation-profile`, and `generate-program`; the numeric aliases `1` through `6` select them in that order. The former identifiers `review-design` and `preview` remain compatibility aliases for `review-package` and `logical-preview`, respectively. `Stage: auto` is convenient when the request and available artifacts make the choice unambiguous; otherwise the skill asks which stage to run. Each invocation performs exactly one stage, while one task may contain successive stage invocations.

Stage selection and stage input are separate dialog steps unless you provide both at once. When you invoke only `$develop-with-aod`, choose a stage first; the skill then asks for one next missing input. For a new application, choose `1` and provide the natural-language goal when asked. Alternatively, put the application goal in the initial invocation: with no existing package, that goal unambiguously selects `create-package`, so no initial stage menu is needed. Stages `2` through `6` primarily require existing artifacts or stage-specific decisions rather than a newly formulated program goal.

After a stage finishes successfully, the skill presents all six stages again, marks their current availability, and recommends one appropriate next action. Reply with its number or name to continue in the same task. You may instead ask a follow-up question or stop; neither response starts another stage.

`<project-slug>` is one lowercase kebab-case filename stem used for the AOD-YAML, context, implementation-profile, optional experience-brief, and generated traceability artifacts. The human-readable project name may differ.

## 1. Create the AOD Package

Invoke `$develop-with-aod` with `Stage: create-package` and a natural-language description of the required application. Project name and slug are optional: when both are blank, the generator derives a concise meaningful name and canonical slug from the application's primary domain and purpose rather than using a generic filename. The process generates:

- `<project-slug>.aod.yaml`, which declares the application behavior;
- `<project-slug>.aod-context.md`, which records package identity and integrity metadata, application-specific design decisions, assumptions, and the environment contract. Its `Design Decisions` section excludes behavior imposed by the AOD framework, profile, or lint rules; an unaccepted generator interpretation is recorded as an assumption instead.

The underlying AOD model permits some paths to be declared implicitly through references, concept bindings, constituents, prefixes, or projections. This framework deliberately makes those paths visible: every inferred or assumed path also appears exactly once in an AOD entry, usually as a declaration-only bare entry `- P`. Such an entry adds no behavior and does not by itself create an Environment Contract row.

Review both files. If you subsequently edit either file, increment the package revision. After editing the AOD-YAML, run `& ./.agents/skills/develop-with-aod/scripts/get_aod_file_digest.ps1 <project-slug>.aod.yaml` from this framework repository and copy its `sha256:...` output into `AOD specification digest` in the context. Update affected context content, then invoke `$develop-with-aod` with `Stage: lint-package` to check the package and resolve material findings.

## 2. Optionally Review the Business Design

Continue in the same task by selecting `Stage: review-package` and use the lint-clean AOD package. Start a fresh task only when you specifically want an independent review perspective or a cleaner context. The review remains optional in either case.

The adaptive review presents at most one unresolved proposal at a time, with a recommendation and stable `BR-nnn` identifier. When a manually edited or older package omits framework-required bare entries, its first item is one nonbehavioral framework-conformance proposal showing every exact addition. It must be accepted before Stage 2 can finalize; `Discard all` may still end the review without changing the package. The numbering is task-local and remains continuous when Stage 2 is invoked repeatedly in the same task; rejected, deferred, superseded, and discarded items still consume their identifiers. Every completed or discarded review reports the next unused identifier before the stage menu. A fresh task starts a fresh sequence, and the counter is not stored in the AOD package. If no reviewer proposal remains, Stage 2 stays open so that you can submit your own change; it does not write files, report completion, or return to the stage menu. Only an explicit standalone `Finish` or `Discard all` terminates the review. The review does not ask you merely to reconfirm behavior already unambiguously declared by AOD-YAML. You may introduce your own change at any turn in natural language, AOD-YAML, context text, or a candidate file. Every user-requested package change is first translated into the same pending proposal form and exact artifact preview as a reviewer proposal; even a complete instruction or supplied patch is not applied until you subsequently reply `Accept` in a later turn. An `Accept` applies only to the proposal that was already pending before that reply. If the same message accepts the current item and adds another request, only the already previewed item is applied; the added request becomes the next pending proposal and requires its own later `Accept`. `Revise: ...` regenerates the preview and remains pending. Every pending proposal ends with exactly: Reply `Accept`, `Accept deferred BR-nnn`, `Reject`, `Revise: ...`, `Defer`, `Discard all`, `Finish`, or ask a follow-up question. `Modify` is not offered as a substitute for `Revise: ...`. Once any mandatory conformance item has been accepted, reply `Finish` whenever you want to stop considering further proposals.

For a pending framework-conformance proposal, `Finish` is the exception to the ordinary termination rule: it leaves that proposal pending because Stage 2 cannot write a nonconforming package. Accept the proposal to continue toward finalization, or use `Discard all` to end the review without changes.

Every pending proposal shows its exact effect before you decide. Each AOD-YAML change is labeled with its group and appears as a red/green unified diff with current draft line numbers and the complete affected declaration, never only detached continuation lines. Context changes outside the Environment Contract similarly show the complete affected item. Every inserted, modified, or removed `ENV-nnn` row uses the same field-by-field `Column | Before | After` table: it always shows complete `ID` and `AOD reference` values, followed only by other columns that actually change; insertions and removals show all fields against `Not present`. Raw replacement rows are not used. When a normative behavioral decision could be placed coherently in either artifact, the review puts it in AOD-YAML and uses the context only for corresponding environment responsibilities or explanatory material. It keeps a simple one-off qualifier inline but gives a newly introduced, independently meaningful business policy its own standing definition instead of continually expanding an already compound declaration. `Accept` applies exactly the displayed semantic patch to the internal drafts and immediately lints the complete draft package. The canonical files remain unchanged until finalization, when all accepted changes are written together, the package revision is incremented once, and the digest is recomputed.

Stage 2 also checks group cohesion without treating groups as semantic scope. It preserves existing group names, order, and declaration placement by default and never repartitions merely by line count. When one group has accumulated distinct reading concerns and become materially difficult to scan, the review must present a pending BR proposal that replaces only that group with two cohesive groups while leaving every other group unchanged. This is the sole editorial BR exception. The preview shows the complete original and replacement groups, and the split is applied only after a subsequent `Accept`, even when the user explicitly requests the regrouping.

`Defer` leaves the current matter open: it applies none of the proposed patch, adds only a `Deferred/unspecified:` remark to the context draft, lints that draft, and continues the review. It does not automatically ask the same question again. Within the same Codex task, `Accept deferred BR-nnn` recalls a known deferred proposal. Stage 2 revalidates its earlier preview and applies it under the same identifier only when its semantic patch is unchanged; if current package changes require a different patch, it shows the same BR as pending again and waits for a separate `Accept`. An unknown or nondeferred identifier fails without changing drafts, allocating a BR, or running lint. BR identifiers are not stored in the package, so a deferred proposal from another task must be identified by content and enters review as a new BR. `Discard all` instead ends Stage 2 and abandons every change and decision remark accumulated in its internal drafts. It writes nothing, so both canonical package files, their revision, and their digest remain exactly as they entered the review. BRs first issued in that discarded review are no longer deferred or eligible for `Accept deferred BR-nnn`; the same subject may later be independently proposed under a new identifier. A BR already deferred before the discarded review returns to its pre-review deferred status. `Finish` is different: it finalizes and writes the currently accepted draft changes.

The review updates the existing `<project-slug>.aod.yaml` and `<project-slug>.aod-context.md`; it creates no additional package file. At finalization it preserves stable `ENV-nnn` identifiers, increments the package revision once when either file changed, recomputes the exact AOD digest, and lints the final package. Any implementation profile or generated program pinned to the former revision is then stale.

## 3. Lint the AOD Package

Select `Stage: lint-package` whenever you want a standalone report without changing the package. This is particularly useful after manual changes to either package file. Supply the AOD-YAML and, for full package validation, its companion context. The stage creates one Markdown lint report; a `PROF001` warning identifies a model-valid path that still needs an explicit bare entry for framework conformance. Use the findings to revise the package through Stage 1, Stage 2, or careful manual editing. Stages 4 through 6 stop rather than silently assume such a missing entry.

## 4. Optionally Generate a Logical Preview

Invoke `$develop-with-aod` with `Stage: logical-preview` to turn the AOD package into one self-contained HTML application for previewing and refining its declared behavior. Choose `allow-visible-simulation` to preview workflows containing non-browser capabilities, or `prohibit-simulation` to require browser-real capabilities only. The HTML is a logical and behavioral preview, not a visual-design specification: its non-governed layout, styling, wording, and presentation mechanisms do not constrain the final program. Final user experience is selected later through the implementation profile and optional experience brief. The simulation choice is likewise logical-preview-only and does not affect implementation profiling or final program generation.

## 5. Choose the Implementation

Invoke `$develop-with-aod` with `Stage: implementation-profile` and the AOD package. Unless a human-readable project name was explicitly supplied or retained from a valid profile, `Project name` is the first pending decision; a name derived from the package remains only a recommendation until accepted. Each turn presents one unnumbered pending decision with a recommended answer. Reply `Accept`, provide another answer, or ask a follow-up without advancing; even when that turn also supplies partial or later-topic choices, the pending decision remains open until explicitly resolved. After target and architecture selection, one gate asks whether you have UX, brand, or content guidance. Declining creates no extra file and selects restrained, accessible internal-tool defaults without an invented brand. Opting in creates `<project-slug>.aod-experience.md`; name or attach any existing brief, guide, logo, or other requested non-secret resource. The brief governs compatible presentation, not behavior. Exact content with business or legal meaning remains in the AOD package.

The dialog prefers a secure, supportable, self-contained deployment: generated components, setup-generated resources, and derived values precede confirmed organizational services and new external prerequisites. For a deployable server boundary, it resolves portable versus host-bound output before asking about a concrete host and recommends a portable runtime boundary when no requirement mandates host binding. It then selects the runtime/OS class, architectures, artifact standard, packaging, and orchestration separately. Containers, OCI, and Linux are conditional technology choices, not synonyms for portability; for example, OCI compatibility does not itself select Linux or an orchestrator. A portable result may be verified on any compatible accessible runtime and later run on a dedicated host; the current machine does not thereby become a profile constraint. The dialog records each provisioning mode, responsibility, delivery, timing, and blocker; externalizes only irreducible or explicitly selected concerns. Application-owned browser authentication receives a complete standards-grounded login-and-session decision, while account provisioning, recovery, and lifecycle remain separate. It also resolves persistent-data lifecycle and real-effect verification. The profile stores stable non-secret settings but no secret or key contents or connection strings. Confirm the summarized choices and readiness blockers when all decisions are resolved. The resulting `<project-slug>.aod-implementation.yaml` defines experience, architecture, stack, runtime portability, deployment, capability realizations, provisioning, and operational policies. When refreshing after a package revision, attach the existing profile and any experience brief as baselines so compatible choices can be retained.

## 6. Generate the Final Program

Invoke `$develop-with-aod` with `Stage: generate-program`, the AOD package, and the confirmed implementation profile. When the profile selects brief mode, also name or attach the exact `<project-slug>.aod-experience.md` and every resource pinned by the profile; otherwise state `None`. The generator treats those inputs as a closed business scope: it may add semantics-preserving technical mechanisms, but it may not infer unspecified business rules, expose internally required data, or add untraceable behavior, persisted domain or audit data, API fields, policies, or effects. The experience brief controls only compatible presentation and editorial choices. The generated `aod-environment-realization.md` records material generator-chosen mechanisms under `Technical Realization Decisions`; review that section as implementation rationale, never as retrospective authorization for added business behavior.

The project also contains `<project-slug>.aod-traceability.yaml`, the generic `aod_traceability.schema.json`, exact provenance copies of the three core governing project artifacts under `aod/`, any brief-mode experience inputs, and a read-only traceability-check command documented in the README. The mapping file links AOD, environment, profile, and experience references to implementation symbols, routes, selectors, schema fields, source markers, assets, and tests; its reverse inventory links every material business or presentation surface back to approved sources. Use it to locate generated code and inspect closed-scope conformance. These artifacts are documentation and verification inputs only and are not loaded by the application at runtime. Rerun the traceability check whenever code, tests, or governing artifacts change.

The generator checks readiness only for applicable execution, verification, or selected deployment hosts, implements every generated responsibility, and creates secure configuration and integration boundaries. It preserves a portable runtime boundary instead of tying output to the machine used for generation. Canonical setup creates and preserves setup-generated values, including secrets, without displaying them; derived values are not separate inputs. Only genuine operator and external-provider items remain in `Required operator inputs`. Use the generated diagnostic and setup, start, update, status, and stop commands rather than reconstructing deployment. A reset remains separate and explicitly confirmed; real-effect verification follows its profile policy. After provisioning a blocker, continue the same task so verification can resume and `aod-environment-realization.md` can be updated; refresh the profile only when a durable choice changes.

When the intended business behavior changes, revise the AOD package before changing the implementation. You may run Stage 1 again from a revised natural-language description, use the Stage 2 co-design review for user-proposed changes, or manually adapt the AOD-YAML and context files. In every case, increment the package revision, recompute the AOD digest, and use Stage 3 to lint the revised package. You may then regenerate downstream artifacts or retain compatible implementation choices by refreshing the existing profile in Stage 5. Because the profile pins the package revision and both file digests, the old profile cannot be used unchanged with the revised package.
